# Client startup priority investigation for 0.13.37

The priority lead does not justify a startup scheduling change. The native Game source selects a Windows `IDLE_PRIORITY_CLASS` during development-mode data loading, but the exact pinned Wine runtime stores that class as metadata. That path does not call Linux `setpriority` or a scheduler API. Replacing it with `NORMAL_PRIORITY_CLASS` would not establish a Linux scheduling improvement.

The physical 0.13.36 reports identify Game Windows PID 624 in session `65a10604bf53486299b97177b11c0711` and PID 844 in session `1682f2cf28bb467a9473f2f1a426036e`. Their independently recorded client startup durations are 264.461 and 264.197 seconds. These are Windows PIDs; neither may be used directly as a Linux `/proc` PID.

The first report contains no explicit task `nice` samples. The second contains 174 samples, all under Kings Row destination preparation, all `nice=5`. They are not Game measurements. Neither report records Game task start times, pre/post `all_data` scheduling, or Windows priority-class readback. Consequently, Game `nice=19`, `SCHED_IDLE`, and startup starvation have not been measured. Live lineage observation also failed to establish authenticated groups in these reports; its missing namespace reads cannot be converted into process identity evidence.

In the unchanged native source, `game_beforeParseArgs` selects ABOVE_NORMAL for BIN creation, NORMAL for production, and IDLE for development; `game_mainLoop` changes development mode to BELOW_NORMAL after initialization. Production foreground/background priority adjustment remains separate. `isDevelopmentMode` depends on `piggs/texts.pigg` and the force-production flag. The launcher does not force production. The source therefore explains the intended Windows class sequence, while actual current-class readback remains unavailable.

Exact Wine commit `b073859675060c9211fcbccfd90e4e87520dc2c2` was reread. `kernelbase/process.c` translates the Win32 class; `ntdll/unix/process.c` sends `SET_PROCESS_INFO_PRIORITY`; `server/process.c` assigns `process->priority`. The thread priority setter similarly stores metadata. The exact runtime Dockerfile pins this Wine source and contains no scheduling-priority patch. This independently confirms the finding already retained in the 0.13.27 zone preparation research.

No source, database, process, priority, graphics, runtime, or native executable was changed or rebuilt for this investigation. There is no new measured speed or RAM benefit.

If scheduling remains a question after the current parsing/cache experiment, add optional read-only observations: at most 64 samples, no faster than five seconds, with current private launch ownership and before/after PID/TID/TGID/start-time checks. Capture nice/policy, CPU ticks, faults, permitted `schedstat`, cgroup and autogroup. A launch-family token initially proves only that family; exact Game-only attribution requires a separately qualified Windows-to-Linux identity binding. Missing permission or identity evidence should produce an omission, without a new startup gate or process mutation. An optional native `GetPriorityClass` readback on the launcher's retained child handle can distinguish Windows class metadata from Linux task scheduling.
