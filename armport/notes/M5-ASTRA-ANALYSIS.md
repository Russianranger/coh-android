## Findings that change the next steps

1. **The sequencer `Reading …` counts are not disk-read counts.** `Common/seq/seqload.c:1124` prints before the cache lookup at 1127. Actual development reload is conditional at 1050–1055 and 1144–1150. `MapServer/src/svr/svr_init.c:2090` already preloads sequencer definitions, and 2112/2116 preload player data. Thus 4,035/2,476 console lines do not establish on-demand file stalls or a missing-preload defect. Instrument actual loads and misses first.
2. **The 67 DbServer threads do not establish idle polling.** `Common/sql/sqlconn.h:15` allows 65 connections; `DBServer/src/sql_fifo.c:26,170` creates 64 SQL workers. `Common/sql/sqltask.cpp:24–26` selects `SemaphoreWorkerPool`; `libs/UtilitiesLib/include/utilitieslib/UtilsCXX/semaphoreworkerpool.hpp:18–23,56–64` waits indefinitely on a semaphore. Measure thread CPU/work rates before reducing workers or changing waits. Copying the client's 2 ms spin into these workers would be an unjustified battery risk.
3. **The Java app already recognizes ARM64.** `ClientRuntime.java:2111–2116` checks ARM64 package/executable identity; `ClientAcceptance.java:16–65` checks ARM64 helpers and stage sequence. The generic failure at Runtime 695–696 does not identify which later predicate failed. Follow-up source execution now identifies a concrete cross-architecture mismatch: `character_reopen_diagnostic.py:47` selects manual sessions; `client_interactive_diagnostic.py:438–441` emits bounded=false/user_controlled=true, but `ClientRuntime.java:2202` unconditionally requires bounded=true. Fix that exact policy predicate while retaining session, Finish, pins, and cleanup checks; this is not missing ARM64-lane support. An extracted execution also confirms that `client_login_diagnostic.py:187–193` can mask an original cleanup failure with the cache-return exception; preserve both causes. The post-zoning cache-return error requires inspection of the original shutdown/ownership failure, not removal of cleanup proof (`character_server_data_cache.py:596–601`, `diagnostic.py:1187–1228`).
4. **Second-zone contention is a strong hypothesis, not a measured tick diagnosis.** Player prediction can mask delayed server updates, but cumulative process CPU and smooth local movement do not isolate server tick, update delivery, or remote-entity interpolation. Keep a measured baseline, then compare with the origin map retired after verified arrival.

## Full-source sibling findings

These are source-confirmed hazards or explicitly labeled candidates, not claims that each caused a Thor failure. Lines in unchanged upstream files are directly inspectable under `upstream/ouroboros/` at the audited SHA.

- **Pointers in int/U32:** `MapServer/src/entity/character_combat_eval.c:33` and dozens of readers use `eval_FetchInt(...,(int*)&ptr)`; stores at 1356–1368 and 1398–1410 truncate Entity/Power/BasePower. This is a separate server implementation from Common's 0036 fix. `MapServer/src/player/badges_server.c:880,893` and `badges_load.c:78,395` have the same paired-store/read problem. Priority ARM64-server blockers; fix paired APIs, not only casts.
- **Pointer-key collisions:** `Common/gameData/store_data.h:9–10`, `store_data.c:225,230`, and `store.c:66` derive a 32-bit stash key from BasePower pointer + level. Distinct addresses with equal low 32 bits can collide. This needs an explicit composite-key test; no Thor shop failure is established.
- **`sizeof(int)` pointer storage:** `MapServer/src/gameSys/Turnstile.c:256,313` clears `Entity *memberEntities[]` at integer width; `MapServer/src/group/groupnetdb.c:67,1152` does the same for `DefTracker *editOrigCheckouts[50]`. ARM64 leaves half the storage uncleared.
- **Pointer formatting:** `Game/src/render/rendertree.c:241` sends `st->tex_bind`/`st->model` to `%08x`; 250 truncates the overloaded texture field for classification. Debug address output is wrong; other uses such as 3414 intentionally hold GL integer IDs. Do not indiscriminately widen IDs.
- **Volatile/compiler-barrier queues:** `DBServer/src/mapcrashreport.c:30–51` publishes raw ring indexes; `libs/UtilitiesLib/src/utils/log.c:227,1170–1187,1297–1334` has a background log queue whose reader does not share the writers' critical section. The SQL pool uses `include/utilitieslib/UtilsCXX/semaphoreworkerpool.hpp:63,114` → `PointerRingChain`; `libs/UtilitiesLib/include/utilitieslib/UtilsCXX/ring.hpp:55–72` / `ringchain.hpp:47–71` use plain pointers and `_ReadBarrier/_WriteBarrier`, which are not an ARM64 hardware publication proof. Audit actual producer/consumer ownership and add extracted concurrency controls before ARM64 server execution.
- **Other varargs / NULL-stand-in siblings:** `Common/persist/persist.c:537` uses `va_arg(key,U8)` despite integer promotion: a distinct candidate requiring a focused control. The third ragdoll creator at `Game/src/entity/entclient.c:2051` passes its unchecked result to interpolation at 2092; `Common/entity/ragdoll.c:102` dereferences it. Current ARM64 cannot establish the preceding live-ragdoll state, so this is a latent contract gap, not a demonstrated reachable crash. The two entrecv creator sites are guarded by 0118.
- **False-positive correction:** the DirMonitor completion key listed in 64BIT-AUDIT is constructed as a U32 index/UID token at `DirMonitor.c:143,154`, decoded at 161; it is not a pointer in this path. `DBServer/src/container.h:352` has an int-based OFFSET macro, but no DBServer call site was found; it is an inactive candidate, not an observed failure.

Searches covered the complete prepared source, including Game, Common, MapServer, DBServer, and libraries: cast patterns `(int|U32|long)`, `(int*)&`, `Array.storage` aliases, `sizeof(int)` allocations/copies/clears, `va_list/va_advance`, pointer printf formats, stand-in return values/callers, and volatile queue/barrier publication. Broad cast matches included hundreds of legitimate IDs/short lengths; grep results were triaged, not blindly counted as bugs. The prepared tree was made with `python3 armport/scripts/patchwork.py init <external-dir>`; `upstream/` was unchanged.
